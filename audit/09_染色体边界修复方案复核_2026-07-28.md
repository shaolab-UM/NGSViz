# 染色体边界修复方案复核

- 日期：2026-07-28
- 范围：`QueryGenomeRange`、`ProcessEachQueryCoorRecord`、`TrimBuffer`、`DataScaler`
- 结论：右边界裁剪本身正确，但整套方案不应按当前形态合入。

## 已确认问题

### [P1] 裁剪后仍固定删除两侧 buffer，会切掉真实端粒坐标

证据：

- `src/main/java/com/NGSViz/ReadBam/QueryGenomeRange.java:76-87` 将查询右端裁剪到 contig length。
- `src/main/java/com/NGSViz/coverageCalculator/TrimBuffer.java:11-14` 仍固定从数组左右各删除 `buf_size`。
- `src/main/java/com/NGSViz/sqldbOperate/ProcessEachQueryCoorRecord.java:123` 无条件调用上述对称修剪。
- `ProcessEachQueryCoorRecord.java:101-104` 以固定修剪后的边界计算 actual flank，因此只能描述已经被错误切短的数组，不能修复数据丢失。

触发算例：

```text
contig length = 1000
region = [950, 995]
flank = 50
buffer = 10

clamp 后查询区间     = [890, 1000]
当前固定 buffer 修剪 = [900, 990]
应保留的目标区间     = [900, 1000]
```

结果：真实坐标 `991..1000` 被删除，其中 `991..995` 甚至属于 region body。

正确做法：

- 分别记录 `actualLeftBuffer` 和 `actualRightBuffer`。
- 目标区间应定义为 `[max(1, anchorStart - flank), min(contigLength, anchorEnd + flank)]`。
- 实际 buffer 为 `desiredStart - queryStart` 和 `queryEnd - desiredEnd`。
- `TrimBuffer` 应接受左右两个长度并进行非对称修剪。
- actual flank 必须基于非对称修剪后的真实边界计算。

### [P1] 空或过短 flank 经现有 `bin()` 仍会产生人工零值

证据：

- `src/main/java/com/NGSViz/coverageCalculator/DataScaler.java:47-64` 允许长度为 0 或小于 `flank_points` 的 flank 进入 `bin()`。
- `DataScaler.java:118-134` 使用 `chunk_size = total_size / num_points`。当 `total_size < num_points` 时，除最后一个 bin 外，其余 bin 宽度均为 0，并被写为 `0.0`。
- 当 `actualRightFlank == 0` 时，整个右侧 flank 输出为零，仍会压低端粒附近 profile。

因此必须先明确缺失 flank 的科学语义：

- 若缺失坐标属于 missing data，应输出 `NaN/NA` 并使下游汇总忽略缺失值。
- 若决定把剩余 flank 拉伸到固定点数，应使用比例边界或插值，不能使用当前整数 `chunk_size` 算法。
- 不应把“不存在的参考坐标”编码为真实零覆盖。

### [P1] point interval 只裁剪查询端点，锚点会失去中心对齐

证据：

- `src/main/java/com/NGSViz/coverageCalculator/DataScaler.java:26-27` 对 point interval 仍将整个不对称数组直接均匀分箱。
- `ProcessEachQueryCoorRecord.java:123` 仍执行固定双侧 buffer 修剪。

右侧裁剪后，middle point 不再位于数组中心；均匀映射到固定数据点会移动 TSS/TES/center 锚点。point interval 需要左右分段缩放或显式 missing-bin 策略，不能只增加 `query_end` clamp。

## 正确部分

- `QueryGenomeRange.java:36-45` 和 `78-87` 使用 BAM header 的 `SAMSequenceRecord.getSequenceLength()` 作为 1-based closed `Interval` 的最大端点，坐标值正确。
- broad interval 记录 genomic-left 与 genomic-right 两侧实际 flank，并在负链最终整体反转，方向处理思路正确。
- `start_pos - effectiveStart` 与 `effectiveEnd - end_pos` 的 closed-coordinate flank 长度公式本身没有 off-by-one；前提是 `effectiveStart/effectiveEnd` 必须来自正确的非对称 buffer 修剪。

## 其他验证结果

- 当前没有覆盖右边界、非对称 buffer、point anchor 和空 flank 的回归测试。
- `mvn -q -Dtest=QueryGenomeRangeTest test` 失败：4 项中 1 项失败，`QueryGenomeRangeTest.java:46` 期望 85、实际 80。原因是 `QueryGenomeRange` 在类加载时缓存配置字段，测试中后续修改 `InputParameterAttributes` 不生效。
- `DataScaler.java:41-45` 的 `midLen < 0` fallback 不应作为科学兜底。正常坐标不变量成立时 `midLen` 应等于 region body 长度；若不成立，应显式报错或跳过记录，避免静默改变为整段均匀分箱。

## 建议修复顺序

1. 先增加四组失败测试：左右边界 broad interval、右边界 point interval、region body 距 contig 末端小于 buffer、实际 flank 小于输出点数。
2. 在 context 中保存 contig length、左右实际 buffer 和修剪后的真实边界。
3. 改为非对称 buffer 修剪，再计算 actual flank。
4. 分别实现 broad 与 point 的边界缩放策略。
5. 明确 missing flank 在 CSV/R 聚合中的表示，再决定使用 `NA` 还是拉伸。
